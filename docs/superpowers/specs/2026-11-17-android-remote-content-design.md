# Android 첫 실행 다운로드·리소스 패치 설계

작성일: 2026-11-17. 상태: **사용자 설계 검토 완료. 다운로드 기반 API 단위 구현, 전체 원격 전환은 후속 진행**.

## 의도와 합의 범위

사용자는 Android 출시, 작은 최초 설치, 첫 실행 리소스 다운로드, 출시 후 잦은 스킬 수치·효과 수정에 대비한 별도 패치 방향에 동의했다. 조사·설계 작성 후 사용자가 설계 검토 완료 및 다음 단계 진행을 지시했다. [첫 구현 계획](../plans/2026-11-17-remote-download-foundation.md)은 다운로드 기반 API와 격리 HTTP 검증 단위다. 게임 에셋 이전, 운영 설정 변경, CDN 계약·비용 발생, 실제 배포는 수행하지 않았다.

아래 세부 동작 중 대화에서 확정하지 않은 항목은 **설계 제안**이다. 실제 저장 공간·초기 다운로드·메모리 목표 수치, 오프라인 허용 정책, 호스팅 업체, 다운로드 화면 문구는 미정이다. 전투 밸런스·보상·MP 규칙을 변경하거나 기획서의 미정 사항을 확정하지 않는다.

## 현재 근거

- 기준은 `adressable-resources-loading` / `90c00c0`, Unity 6000.5.0f1 / Addressables 2.9.1이다.
- [조사 보고서](../../AI/AndroidResourceLoadingAudit.md), [원본 용량 요약](../../AI/ResourceLoadingInventory.json), [개별 경로](../../AI/ResourceLoadingInventory.csv)를 참조한다. 원본 75.87 MiB는 앱 크기가 아니다. 씬·Resources GUID 후보 합집합 원본은 34.68 MiB이며 실제 빌드 포함·압축·제거 결과를 대체하지 않는다.
- 실제 진입은 타이틀→로딩→로비→로딩→MainScene이다. LoadScene은 빈 preloadLabel/requireSkillData=false로 테스트 준비를 허용하고, 원격 그룹·카탈로그·호스트가 없다.
- `Managers.Resource.Load<T>`는 캐시 조회이며, `PreloadAsync`는 에셋 메모리 로딩이다. 전투 표 `CombatSkillTable`과 별도 `SkillData`의 준비 의미를 구분해야 한다.

## 검토한 접근과 선택 방향

| 접근 | 장점 | 비용·제한 | 이번 방향 |
|---|---|---|---|
| Resources 유지, 준비 진입만 통합 | 연결 보존, 작업이 작음 | 첫 설치 분리·원격 패치 목표를 충족하지 못함 | 초기 질문에서는 추천했으나 출시 목표 확인 후 제외 |
| Google Play Asset Delivery 중심 | Play가 호스팅·전달, 별도 CDN 운영 축소 | 콘텐츠 배포가 앱 릴리스에 연결됨. Play 이외 확장과 독립 패치 요구에 제약 | 이번 독립 패치의 주 배포 방식으로 선택하지 않음 |
| Addressables 원격 번들+CDN | 첫 다운로드·리소스 독립 배포, 플랫폼별 확장 | 호스팅 비용·호환 버전·릴리스·복구 운영 필요 | 대화에서 동의한 방향. 제공 업체는 미정 |

Addressables와 PAD는 서로 대체하는 동일 계층 기술이 아니다. 향후 일부 대용량 고정 에셋에 PAD를 병용할 수 있지만 첫 구현에는 섞지 않는다.

## 목표와 성공 기준

- 앱에 시작·다운로드·복구에 필요한 최소한의 로컬 에셋을 둔다. 필수 다운로드 리소스가 없어도 오류·진행·재시도 UI는 표시돼야 한다.
- 호환 릴리스의 필수 콘텐츠가 준비되기 전 로비/전투로 진행하지 않는다. 게임 진입 시 이번 판에 필요한 메모리 준비도 별도로 완료한다.
- 재실행 시 유효한 다운로드 캐시를 재사용한다. 캐시가 없어졌으면 다시 필요한 양을 조회하며 `첫 실행 완료` bool만으로 건너뛰지 않는다.
- 코드와 데이터 형식이 같은 앱에서 그림·사운드·전투 수치 패치가 가능해야 한다. 새로운 C# 동작·지원하지 않는 데이터 형식·Unity/Addressables 변경은 앱 업데이트로 처리한다.
- 실제 Android 빌드의 기본 다운로드 크기, 첫 콘텐츠 다운로드, 설치 후 저장 공간, 최대 메모리를 각각 측정한다. 목표 MiB와 지원 기기는 측정 후 합의한다.

## 역할과 기존 계약 보존

| 담당 | 소유할 책임 | 보존할 점 |
|---|---|---|
| Managers | 앱 실행 중 고정한 콘텐츠 릴리스, 준비 작업/상태, 진입 허용 여부 | 영속 코루틴 소유권·동시 준비 가드·실패 전환 차단 |
| ResourceManager | 카탈로그·용량 조회·다운로드·에셋 로딩 핸들, 메모리 캐시와 해제 | 기존 Load/LoadAllAsync/PreloadAsync/Instantiate 호출 호환, 동일 요청 공유 |
| DataManager 및 기존 표 클래스 | 호환 형식 검증, 검증 완료된 데이터 게시 | CombatSkillTable과 SkillData를 혼동하지 않음, 공개 조회 API 보존 |
| LoadScene/UI_LoadScene | 단계·바이트 진행·실패 원인·재시도 표현 | UI가 핸들 소유권이나 새 전역 상태를 갖지 않음 |
| SceneManagerEx | 목적지 예약·검증·전환 순서 | 기존 enum 씬 이름·Build List 경로·정리 한 프레임 보장 보존 |
| 플레이어·전투 연출 | 검증된 표·준비된 그림 사용, 생성 Sprite/Material 수명 | HP/MP·공격·패링 규칙과 수치 보존 |

새 전역 매니저·싱글톤·이벤트 프레임워크를 추가하지 않는다. 필요한 직렬화된 릴리스 정보 타입이나 요청 결과 타입은 기존 모듈 안에서 정의한다. 이번 설계는 API 이름을 임의로 확정하지 않는다.

현재 `GameDataReady`는 별도 SkillData 준비 여부에 연결돼 있다. 새 원격 전투 준비 완료를 이 bool이나 `TestReady`로 대신 표현하지 않는다. 구현 시 기존 enum/호출을 보존하면서 다운로드 준비와 실제 전투 표 검증 결과를 명시적으로 구분하고, 출시 경로에서는 필수 콘텐츠가 없는데 테스트 준비로 진입하지 못하도록 한다. 에디터의 기존 로컬 테스트 경로는 명시적인 개발 설정으로 유지한다.

## 세 가지 서로 다른 수명

1. **다운로드 캐시:** 번들을 기기 디스크에 보관한다. 에셋 해제나 씬 이동으로 삭제하지 않는다. 다운로드 전용 작업은 `GetDownloadSizeAsync`와 `DownloadDependenciesAsync`를 사용한다.
2. **메모리 에셋:** 이번 실행·전투에서 필요한 에셋만 로딩한다. 바이트 다운로드 완료가 메모리 준비 완료를 뜻하지 않는다. 전부 다운로드했어도 전부 한꺼번에 로딩하지 않는다.
3. **파생 객체:** `LightSkillVisuals`가 만든 Sprite·Material·프레임 사전과 데이터 정적 사전이다. 참조하는 이펙트/풀 객체를 먼저 정리한 뒤 생성 객체, 원본 핸들 순서로 해제한다. 프로젝트 임포트 에셋과 `new Material`/`Sprite.Create` 객체의 소유권을 구분한다.

기존 `Managers.Clear`의 씬 이동 시 Resource 캐시 보존 계약을 몰래 바꾸지 않는다. 초기 시범은 릴리스를 프로세스 시작 시 고정하고 종료까지 유지한다. 전체 이전 단계에서는 앱 공통/전투 요청의 소유 범위를 추적해 타이틀 복귀 시 전투 참조만 반환하도록 확장한다. 공용 핸들을 전투 종료 때 일괄 Clear해서 로딩·로비 UI까지 끊지 않는다.

## 앱 포함과 원격 그룹 제안

| 범위 | 후보 | 배포·로딩 원칙 |
|---|---|---|
| 로컬 시작 필수 | Title/Load UI, 필수 한글·숫자 폰트, 연결 실패·재시도 표시 | 원격 콘텐츠를 참조하지 않아도 표시. 로컬 UI 폰트와 게임 폰트 공유 비용 점검 |
| 공통 원격 | 실제 전투·성장 표, 카드 아이콘, 공통 전투 연출 | 첫 플레이 전에 다운로드. 작은 자주 바뀌는 데이터는 큰 그림 묶음과 분리 |
| 스킬 연출 | Fx Texture+Frames JSON, Blaze Sprite, 재질·셰이더 의존성 | 한 효과의 그림·프레임 정보는 호환 버전으로 함께 준비. 업데이트 빈도와 측정에 따라 묶음 크기 결정 |
| 전투 콘텐츠 | MainScene HUD·적·보스·맵 프리팹/이미지/사운드 | 직접 참조를 분리한 대상부터 이전. 필수 첫 판 콘텐츠는 전투 전 다운로드 |
| 이후 선택 콘텐츠 | 추후 확정될 스테이지·스킨 등 | 아직 없는 기획을 구현하지 않음. 향후 필요 시 진입 전에 다운로드 |

라벨은 다운로드·메모리 준비 대상 선택용이고 실제 다운로드 단위는 번들 및 그 의존성이다. 폴더 하나 전체를 거대한 번들로 묶거나 모든 작은 에셋을 각각 번들로 만드는 결정을 먼저 하지 않는다. 한 수치 변경이 대형 이펙트 재다운로드로 번지지 않게 Build Layout과 패치 전후 변경 번들을 확인한다.

**설치 크기를 줄이려면** 이전 대상은 Resources 밖으로 `.meta`와 함께 이동해 GUID를 보존하고, 로컬 씬/프리팹에서 끌어오는 직접 참조도 분리해야 한다. `2.Resources`는 자동 포함 폴더가 아니므로 이름만 바꾸는 조치는 하지 않는다. Shader.Find만 사용하는 셰이더가 Android에서 제거되지 않도록 명시적 머티리얼/셰이더 의존성과 변형을 검증한다.

MainScene은 첫 단계에서 로컬 유지한다. 최종적으로 크게 줄일 필요가 있으면 **기존 MainScene 자체의 원격 이전** 또는 **MainScene의 대형 콘텐츠를 Addressable 프리팹으로 분리** 중 BuildReport에 근거해 결정한다. 새 게임 씬을 만들거나 GiungScene을 이용하지 않는다. 씬 원격 이전 시 현재 `CanStreamedLevelBeLoaded` 및 일반 SceneManager 계약도 함께 설계해야 하므로 첫 시범에 섞지 않는다.

## 실행 순서 제안

현재 타이틀→로딩→로비, 로비→로딩→MainScene 흐름을 유지하며 LoadScene 진입 목적에 따라 준비 범위를 다르게 한다. 전투용 테스트 진입은 기존과 같이 MainScene 직접 실행을 지원하는 개발 설정으로 구분한다.

1. 로컬 타이틀을 표시한다. 최초 시작 요청에서 중복 버튼 입력을 막고 기존 LoadScene으로 이동한다.
2. 호환 릴리스 정보 조회 → 카탈로그 선택/로드 → 필수 라벨의 추가 다운로드 바이트 조회. 확인 중인 단계와 다운로드 바이트 진행을 구분한다.
3. 추가 데이터가 있으면 용량·네트워크 안내 후 사용자 다운로드 동의를 받는 UI를 제공한다. 정확한 문구·버튼 배치·모바일 데이터 정책은 미정이다.
4. 다운로드 중 `GetDownloadStatus`의 수신/전체 바이트를 표시한다. 기존 에셋 처리 개수와 `PercentComplete`를 다운로드 바이트 퍼센트로 표시하지 않는다. 전체 0바이트면 캐시 확인 단계로 처리한다.
5. 필수 에셋 존재·호환 데이터·파생 준비를 검증한다. 작은 데이터와 로비 필수 에셋만 메모리에 준비하고 로비에 진입한다.
6. 로비에서 시작하면 이번 전투 라벨과 데이터 스냅샷을 고정하고 필요한 에셋·효과 프레임을 준비한다. 모두 성공해야 MainScene에 진입한다.
7. 한 판 진행 중 카탈로그·수치·그림을 갈아끼우지 않는다. 첫 버전은 새 패치를 다음 앱 실행에 적용한다.

제안 상태는 `확인 중 / 동의 대기 / 다운로드 중 / 검증·로딩 중 / 준비 완료 / 실패`다. 구체 팝업 내용은 만들지 않는다. 다운로드 실패·시간 초과·공간 부족·호환 앱 없음·카탈로그 누락을 구분 가능한 결과로 반환하고 UI는 재시도를 제공한다. 같은 요청의 동시 대기와 호출자 파괴는 기존 영속 작업 소유권 계약을 유지한다. 취소된 이전 작업이 뒤늦게 Ready나 새 캐시를 덮지 못하도록 세대를 검사한다.

다운로드 중 종료 시 완료된 번들은 캐시로 재사용한다. **중단된 번들 파일의 바이트 단위 이어받기를 보장하지 않는다.** 재시작 시 크기를 다시 조회한다. 실패하면 기존 정상 릴리스를 삭제하거나 다운로드 완료로 기록하지 않는다. 디스크 여유는 다운로드 바이트와 같다고 가정하지 않고 새 번들·이전 정상 번들·캐시 변환에 필요한 공간을 실측해 산정한다.

오프라인 정책은 미정이다. 제안은 첫 필수 다운로드가 없으면 진입 차단, 기존 정상·호환 콘텐츠가 모두 남아 있으면 오프라인 플레이를 허용하는 것이다. 서버 기능이나 강제 업데이트 정책이 추가되면 다시 결정한다. 카탈로그 갱신 실패를 무조건 정상으로 숨기지 않는다.

## 릴리스·호환·복구 제안

- 앱 호환 계열과 플랫폼별로 원격 경로를 분리한다. 운영용 앱이 하나의 전 플랫폼 `latest` 카탈로그를 무조건 받게 하지 않는다.
- 앱 기본 카탈로그는 로컬 시작 필수 에셋만 담고 자동 원격 카탈로그 갱신을 비활성화한다. 호환 릴리스 정보를 먼저 확인한 뒤 해당 릴리스의 불변 URL을 `LoadContentCatalogAsync`로 선택한다. 한 프로세스에는 하나의 게임 콘텐츠 카탈로그만 활성화한다. 기본 로컬 키와 원격 게임 키도 충돌하지 않게 나눈다. 이전 정상 카탈로그를 선택하는 복구는 새 프로세스 시작에서 수행한다. 이 순서로 구버전 앱이 호환 확인 전에 새 카탈로그를 받는 일을 막는다.
- 작고 버전이 있는 릴리스 정보에는 플랫폼, 앱 호환 계열/최소 지원 앱, 데이터 schemaVersion, contentVersion, 카탈로그 URL/검증 정보, 필수 라벨을 둔다. 정확한 필드와 서명 여부는 구현 설계에서 확정한다. HTTPS와 콘텐츠 무결성 검증을 사용한다.
- 같은 앱에서 읽을 수 없는 필드·열거값·새 코드 동작은 콘텐츠 패치로 배포하지 않는다. 클라이언트 버전별 데이터 검증기를 실행한다. 잘못된 ID·중복·누락 그림·틀린 프레임 크기·지원하지 않는 판정은 이전 정상 데이터를 대체하기 전에 거절한다.
- 전투 데이터는 전체 검증 후 한 번에 게시한다. 스킬 표만 v2, 효과 JSON은 v1인 혼합 상태로 게임을 시작하지 않는다. 주소는 안정적으로 유지하고 내용 버전은 릴리스로 구분한다. 기존 아이콘 표의 `SkillIcon_10025`와 실제 `Skill_10025.png`처럼 fallback에 의존하는 키는 매핑 계약을 먼저 정리한다.
- 카탈로그 갱신은 에셋 로딩 전에 수행한다. 같은 프로세스에서 카탈로그를 바꾸면서 기존 주소/위치 충돌을 우회하지 않는다. 복구 릴리스를 적용해야 하면 재시작을 요구한다.
- 정상 릴리스 기록은 카탈로그·필수 번들 다운로드와 데이터·대표 에셋 검증이 끝난 후에만 교체한다. 이전 정상 카탈로그/번들을 보존한다. `UpdateCatalogs`만 호출했다고 원자적 설치·롤백이 제공되는 것으로 간주하지 않는다.
- 여기서 정상은 준비 검사 통과를 뜻하며 모든 전투 동작의 무결성을 보증하지 않는다. 이후 MainScene 진입 전 실제 전투 준비가 실패해도 이전 정상 릴리스로 재시작 복구할 수 있어야 한다. 이전 복구 릴리스는 새 릴리스 기록 승격과 동시에 삭제하지 않는다. 시범 검증에는 대표 효과뿐 아니라 준비 실패를 의도적으로 발생시킨 복구도 포함한다.
- 새 릴리스가 부분 실패하면 이전 정상 카탈로그 경로를 선택해 재시작 후 같은 릴리스로 준비한다. 카탈로그가 로컬에서도 없어졌거나 필수 번들이 삭제됐다면 온라인 복구가 필요하다. 활성 릴리스와 이전 복구 릴리스가 사용하는 디스크 캐시는 자동 전체 삭제하지 않는다. 캐시 정리는 보존 정책 확정 후 수행한다.
- 배포는 번들 업로드·존재 확인 → 새 카탈로그/해시 업로드 → 테스트 → 호환 릴리스 선택 정보 전환 순서로 한다. 번들은 내용에 따라 불변 이름으로 배포하고 기존 앱이 참조하는 파일을 덮어쓰거나 조기 삭제하지 않는다. CDN 캐시 TTL/무효화도 파일 역할별로 정한다.
- 플랫폼·앱 정식 릴리스별 원본 `addressables_content_state.bin`, 빌드 도구/패키지 버전, 카탈로그·해시·번들·Build Layout·Git 커밋을 보존한다. 후속 콘텐츠 패치는 해당 앱 최초 릴리스의 content state를 기준으로 빌드한다.
- 배포 실패 시 직전 정상 릴리스로 선택 정보를 되돌리고, 신규 설치와 이미 패치한 설치 모두 복구되는지 확인한다. 구버전 앱 호환 경로는 계속 보존한다.

## 단계별 전환과 확인 기준

### 0. 기준 측정

이번 원본 조사를 기준으로 Android AAB/기기 설치·메모리의 기준선을 별도 측정한다. 사용자 에디터의 같은 프로젝트를 두 번째로 열지 않는다. 필요하면 짧은 임시 검증 복사본을 쓰고 Play From Title 간섭을 피한다. BuildReport/Build Layout의 실제 포함 에셋, 엔진·코드·폰트·텍스처 비중을 각각 기록한다.

### 1. 작은 원격 시범

후보는 전투 표 `CombatSkillTable.json`과 기존 수살(10025)의 `WaterArrow.png` + `Fx/Frames/WaterArrow.json`, 실제 아이콘 `Skill_10025.png`다. 수치·판정·MP·파일 내용은 바꾸지 않고 공급 경로만 바꾼다. 표 전체에 들어 있는 다른 스킬의 리소스는 개발용 로컬 경로를 유지하되 이전한 대상이 로컬 fallback으로 조용히 성공하지 못하게 구분한다. 이 시범을 전체 출시 준비 완료로 판단하지 않는다.

기존 직렬화 참조·GUID를 보존하고, 호출부의 동기 조회는 사전 준비한 캐시를 읽게 한다. 별도의 가짜 전투 데이터는 넣지 않는다. 검증용 콘텐츠 변경은 로컬/테스트 배포에만 만들고 승인 없는 밸런스 변경을 운영에 배포하지 않는다.

시범 완료 기준:

| 조건 | 기대 결과 |
|---|---|
| Android 깨끗한 신규 설치 | 필수 양 표시·다운로드 후 로비/전투 진입, 수살 그림·판정 유지 |
| 같은 앱 두 번째 실행 | 변경·삭제 없으면 대상 번들 추가 다운로드 0, 캐시에서 준비 |
| 앱 파일 그대로 콘텐츠 v2 배포 | 테스트용 변경 에셋이 다음 실행에 반영, 변경 번들과 의존성만 다운로드 |
| 네트워크 끊김·앱 종료 | 잘못된 준비 완료 기록 없음, 재시도에서 완료 번들 재사용 |
| 틀린 표·프레임·없는 번들·호환 안 되는 릴리스 | 게임 진입 차단 또는 정책에 따른 이전 정상 복구, 혼합 버전 금지 |
| 캐시 삭제·공간 부족 | 크기 재조회, 재다운로드/공간 안내, 멈춘 진행 표시나 무한 재시도 없음 |
| 릴리스 선택 정보 복구 | 재시작 후 이전 정상 데이터·효과로 동일 릴리스 준비 |

### 2. 데이터·효과 확대

PlayerStatTable·아이콘·LightSkills·방어/보스/아이템 효과를 순서대로 이전한다. 호출·파생 캐시 해제 및 원본 핸들 수명을 함께 변경한다. 단계마다 기존 전투 회귀 테스트와 메모리·다운로드량을 확인한다. 임포트 압축은 효과 품질 검증과 분리해 최소 변경한다.

### 3. 설치 크기와 운영 마무리

MainScene 직접 참조와 공통 폰트를 분석해 실제 큰 대상부터 분리한다. Analyze에서 Resources/Scene 중복 의존성과 공유 번들 결합을 확인하고 AAB·기기로 절감량을 비교한다. 정식 CDN·운영/테스트 분리·보존 기간·오프라인/필수 업데이트 정책·지원 기기·목표 용량을 확정한 뒤 배포 자동화와 출시 검증을 진행한다.

## 검증 범위와 사용자 확인

초기 조사 단계는 정적 조사·문서화만 수행해 실행 테스트 0개였다. 후속 다운로드 기반 단위에서 Windows Editor의 실제 HTTP 검증 번들·디스크 캐시·공급 경계를 테스트했다. 정확한 최신 결과는 Handoff와 첫 구현 계획에 기록한다. 과거 36개 통과 기록을 새 검증으로 재사용하지 않는다. 출시용 카탈로그·게임 콘텐츠 번들·운영 CDN·Android 빌드·기기는 여전히 미검증이다.

사용자는 조사 보고서의 CSV/수치와 이 문서의 역할·다운로드/로딩 분리·복구 방향을 확인했다. 현재 Unity에서 바뀐 버튼이나 다운로드 화면은 없어야 한다. 직접 메뉴·MainScene 참조 확인 순서와 이상 시 볼 항목은 조사 보고서 마지막 절, 새 기반 검증은 tools/RemoteContentValidation/README.md에 있다. 이후 호환 릴리스·카탈로그·동의 UI·게임 공급 경로를 연결할 때 각 단위의 구체 구현 계획과 검증을 추가한다.
